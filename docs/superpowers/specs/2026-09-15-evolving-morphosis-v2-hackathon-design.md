# Evolving Morphosis v2 — Hackathon Architecture

## Objective
The hackathon build must prove that Evolving Morphosis is designed for models that do not exist yet. It cannot depend on hard-coded model names or a closed capability enum.

## Public thesis
A future model enters through a minimal bootstrap boundary. Its advertised capabilities are treated as unverified priors. Morphosis observes behavior through probes, can register novel namespaced capabilities without changing the stable core schema, can propose compatibility/runtime adaptations, and packages every proposed change into an evidence-hashed Evolution Bundle.

Runtime/config adaptations may auto-apply only after all tests and hard invariants pass. Any source-code patch generated by a model is marked `HUMAN_APPROVAL_REQUIRED` and never auto-merged.

## Public architecture
1. **Bootstrap Handshake** — identify unknown candidate, provider/endpoint, transport surface, provenance, and candidate hash.
2. **Extensible Capability Registry** — namespaced capabilities; unknown capabilities default to UNKNOWN.
3. **Adaptive Probes** — built-in probes for known capabilities; bounded candidate-proposed probes for novel claims.
4. **Workload Contract** — required capabilities, hard invariants, regression limits, cost/latency budgets, promotion margin.
5. **Compatibility Compiler** — propose adapter selection, schema transforms, tool wrappers, context strategies, or portable fallbacks.
6. **Sandbox Gate** — execute generated probes/integration changes with no unapproved external side effects.
7. **Evolution Bundle** — immutable manifest containing candidate identity, observed capabilities, proposed changes, tests/evals, rollback, evidence hashes, and PROMOTE/HOLD/REJECT recommendation.
8. **Promotion Boundary** — reversible runtime/config changes may auto-apply after all gates; source changes stop for human approval.
9. **Continuous Requalification** — drift and regressions can trigger requalification or rollback.

## Demo contract
The demo introduces a synthetic `future-model-x` with a novel capability identifier that is absent from the repository beforehand. Morphosis must:
- bootstrap the unknown model without a pre-existing adapter name;
- record the novel capability as UNKNOWN first;
- accept a bounded probe proposal;
- independently verify the probe result;
- add the observed capability to the manifest without editing the core schema;
- propose an integration/runtime adaptation;
- produce a deterministic Evolution Bundle;
- show that a runtime-only safe bundle can be auto-applicable;
- show that a source-code patch is blocked at human approval.

## Hard invariants
- unknown never means supported;
- self-report never equals proof;
- candidate cannot decide its own pass/fail;
- failed evolution never mutates the incumbent;
- automatic changes require rollback metadata;
- hard invariants, evidence semantics, evaluator logic, and source-merge approval are outside the auto-writable surface;
- a better aggregate score cannot compensate for an invariant failure.

## UI changes
The approved raspberry/black Morphosis console must expose the v2 lifecycle visually:
`Unknown Model → Bootstrap → Discover → Probe → Extend Schema → Compile Adaptation → Sandbox → Evolution Bundle → Gate → Shadow/Canary → Requalify`.

The Architecture view must add an explicit `NOVEL CAPABILITY REGISTRY`, `EVOLUTION BUNDLE`, and `HUMAN MERGE GATE`, and distinguish automatic runtime evolution from human-approved source evolution.

## Test requirements
1. unknown future model needs no hard-coded model entry;
2. novel capability registers dynamically;
3. self-report remains unverified before probe evidence;
4. malformed/unsafe generated probe is rejected;
5. compatibility fallback is represented honestly as adapted rather than native;
6. invariant failure forces REJECT;
7. runtime/config bundle can be marked auto-applicable only with rollback;
8. source-code bundle always requires human approval;
9. Evolution Bundle hash is deterministic and tamper-evident;
10. failed evolution leaves incumbent unchanged;
11. drift can trigger requalification.

## Scope protection
The public build demonstrates the protocol and proof. Proprietary routing heuristics, private scoring strategies, private memory/identity architecture, long-term cross-agent learning, and private AM/Animantum internals are excluded.
